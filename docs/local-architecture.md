# Local review foundation

The CLI is the shared engine; the VS Code extension is a thin client. The older FastAPI/dashboard/demo work remains as an inactive historical prototype and is not invoked by this workflow.

Input is a local Git worktree path. The engine resolves the root and HEAD, reads HEAD's tree and blobs with Git plumbing, enumerates tracked index paths and non-ignored untracked paths, and reads current tracked files from disk. HEAD versus final working-tree content includes the combined effect of staged and unstaged changes; staged changes subsequently undone in the worktree have no net difference. Untracked files are listed separately, not analyzed. An unborn branch returns a missing-HEAD analysis error rather than assuming an empty baseline.

Git subprocesses use argument arrays, no shell, no optional locks, no fsmonitor, no lazy object fetching, no hooks, no pagers and no project-provided configuration commands. No working-tree Git diff, project dependencies, scripts, compiler config, hooks, clean/smudge filters or textconv drivers run. Line differences are computed inside the tool. Symlinks, submodules, unsupported languages, binaries, default exclusions, oversize files and parsing failures are reported. Worktree path components are checked against symlinks before reads. Files are bounded to 1 MiB; Git output and execution time are bounded. Concurrent file edits are not an atomic snapshot: save buffers and avoid modifying files during review.

The TypeScript parser creates syntax trees only; it does not resolve imports or load tsconfig/plugins. CP001 recognizes direct console.log/info/warn/error/debug/trace calls with a direct sensitive-name identifier or property argument. CP002 additionally follows supported authorization-header reads through straight-line function-local assignments; its exact syntax and stopping rules are documented in [authorization flow](authorization-flow.md). Comment and string contents are not searched. Old/new signatures of methods and direct sensitive arguments prevent unchanged pre-existing sensitive logging from becoming findings due solely to formatting or unrelated label-string changes. Findings require overlap with added lines. Evidence contains recognized console methods, CP001 allowlisted name categories and CP002 identifier/location metadata, never source snippets or literal values.

Schema 3.0.0 records HEAD, inspected files, changed line ranges in old and new coordinates, findings with per-finding runtime/newness status, CP002 source/assignment/sink evidence, located analysis-limit notes, skips, errors, exclusions, untracked paths, processing completeness, scoped coverage and runtime_verification=false. Paths are metadata and are not value-redacted. The engine performs no network calls, telemetry, tests or edits. Git lazy fetch is disabled for partial clones; missing objects cause errors.

The extension bundles the exact same CLI and parser with esbuild, invokes it via a trusted system Node executable using execFile, validates output, and maps findings to native TreeView items and diagnostics. It never runs a workspace-provided CLI or asks an AI assistant for results. Progress says that analysis is running; no synthetic percentages. Old diagnostics are cleared at start and after workspace changes. Nonzero engine exit with structured partial results is shown as incomplete, not clean.

## Primary API references

The parser uses [TypeScript’s Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API), creating source files without a compiler project. The editor integration follows the [VS Code Tree View API](https://code.visualstudio.com/api/extension-guides/tree-view) and [Extension API](https://code.visualstudio.com/api/). Git object reads use its explicit [no-lazy-fetch and no-optional-locks options](https://git-scm.com/docs/git). These are implementation references, not novelty claims.

The local VSIX is produced using `vsce package` only. Packaging dependencies are not bundled into the extension; a patched minimatch override is applied only to the packager. The archive contains the engine/parser, extension adapter, README and third-party licenses. The packaged-install harness installs that archive into a fresh extensions directory, verifies its installed ID/version and loads the target from that directory; a separate development test driver exercises it. This is distinct from a development-source host test. See [packaged-install verification](packaged-install.md).
